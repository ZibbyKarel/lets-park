# 0025 – Primary keys are client-generated UUID v7

**Date:** 2026-08-28 · **Status:** accepted · **Follows on from:** `doc/decision/0016-*`

## What

Every entity table has `id UUID` with `@default(uuid(7))`, i.e. **UUID version
7** generated by the Prisma Client. The column is a native `UUID`, not `TEXT`.

The exception is `ReservationWindowSettings.id` – a fixed `INTEGER` of `1` (see
`doc/decision/0026-*`).

## Why

`doc/decision/0016-*` binds Task 9 to UUID (not cuid, not autoincrement) and
**deliberately leaves the version open**: `idSchema` is `z.uuid()`, and the
client never reads the id. Choosing the version is therefore purely a storage
performance question.

**Why v7, not v4.** UUIDv7 has a timestamp in its first 48 bits, so newly
generated ids increase monotonically. On a primary key (a B-tree), that means
writes keep landing on the same, most-recent index page, instead of a random
v4 scattering writes across the whole index. The difference is only
noticeable on large tables – our `Reservation` will grow by roughly tens of
rows a day – but it costs nothing, so there's no reason to pick the worse
option.

Side effect: `ORDER BY id` roughly matches creation order. **Nothing may rely
on that** – the waitlist is ordered by `createdAt` with `id` as a tiebreaker,
not by `id`.

**Why the client generates it, not the database.** Postgres 17 has no built-in
`uuidv7()` (that only arrives in 18); `gen_random_uuid()` only produces v4. An
alternative would be `@default(dbgenerated("gen_random_uuid()"))`, but that
means v4, and also two different id sources depending on whether a row is
created through Prisma or through raw SQL.

**A consequence worth remembering:** a manual `INSERT` in SQL (a migration, a
fix in `psql`) must supply `id` itself, since the column has no `DEFAULT`.
Today this affects only one place – the singleton `INSERT` in the init
migration, where `id` is a fixed `1` anyway.

**Why a native `UUID`, not `TEXT`.** 16 bytes instead of 36, faster
comparisons, and the database rejects garbage right at write time.

## How

```prisma
model User {
  id String @id @default(uuid(7)) @db.Uuid
  …
}
```

The test `schema-contract-parity.spec.ts` guards against the id's wire type
drifting from the contract; `migration-sql.spec.ts` guards that the column is
`UUID`.

## Risk if this is wrong

Changing the id format after deployment means a data migration, not a schema
tweak – which is why this is recorded here and not only in `doc/database.md`.
If v7 turns out to be a problem (for instance, because it leaks the record's
creation time – which it genuinely does), moving to v4 is a one-line schema
change **for new rows**; existing ids stay v7, and nothing breaks, since the
contract doesn't enforce a version.
