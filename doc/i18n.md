# i18n – `libs/i18n`

Task 17 from `doc/implementation-plan.md`. `libs/i18n` is the **only place in
the entire workspace allowed to import `next-intl`** (enforced by
`no-restricted-imports` in the root `eslint.config.mjs`, see
`doc/workspace.md`, "Wrapper layers" section). FE feature code imports only
`@lets-park/i18n`.

The lib carries the tags `type:util`, `scope:web` (`doc/workspace.md`).
`scope:web` is deliberate here and load-bearing: `apps/api` (`scope:api`)
cannot depend on `libs/i18n`, so `next-intl` has no path into the backend.

## What the lib does

1. **Re-exports the Europe/Prague date logic from `libs/shared-types`** under
   the same names (`doc/decision/0003-date-helpers-in-shared-types.md`) —
   `DateOnly`, `todayInPrague`, `isWeekend`, `isCzechPublicHoliday`,
   `czechPublicHolidayOn`, `isBusinessDay`, `monthLockState`, … Feature code
   imports only `@lets-park/i18n`, never `@lets-park/shared-types` directly.
2. **Formats dates in Czech** (`lib/dates.ts`) exactly as shown in
   `doc/design/screens/07-lot.png` and `05-admin-window.png`.
3. **Translates contract error codes** into a readable Czech sentence
   (`lib/errors.ts`, `lib/messages.ts`).
4. **`IntlProvider`** (`lib/provider.tsx`) — a thin wrapper over
   `NextIntlClientProvider`, hard-set to the app's single locale (`cs`,
   `Europe/Prague`) — the MVP scope has no language switching.

## Date formatting

| function | example | month form |
| --- | --- | --- |
| `formatFullDate(date)` | `pondělí 28. září 2026` ("Monday, September 28, 2026") | genitive |
| `formatDayAndMonth(date)` | `25. srpna` ("the 25th of August") | genitive |
| `formatMonthAndYear(date)` | `srpen 2026` ("August 2026") | nominative |
| `formatMonthName(month)` | `září` ("September") | nominative |
| `formatYear(year)` | `2026` | — |

Czech declines month names, and `Intl`/next-intl only produce the genitive
when `day` is part of the same formatting call — hence four separate
functions instead of one parameterized one. The detailed reasoning and a
verified example (August, where the nominative and genitive differ, unlike
September, where they coincide) is in
`doc/decision/0024-czech-month-declension-genitive-vs-nominative.md`.

The input is always a `DateOnly` (`YYYY-MM-DD`, a calendar day with no
timezone) — never an instant. The functions internally convert it to UTC
midnight and format with `timeZone: 'UTC'`, so the displayed day is never
shifted by the Europe/Prague zone or a daylight-saving transition.

## Error codes

`translateErrorCode(code: ErrorCode): string` (`lib/errors.ts`) returns a Czech
sentence for any of the twelve codes in `ERROR_CODES`
(`libs/contract/src/schemas/errors.ts`, `doc/contract.md`). Coverage is
complete and guarded by a test that iterates `ERROR_CODES` — a new value added
to the contract without a matching entry in `csMessages.errors` fails
`errors.spec.ts`, rather than only showing up once a user sees a raw enum
name.

`OUT_OF_HORIZON` and `RESERVATIONS_LOCKED` deliberately have distinct
sentences — the first says "not open yet", the second "already closed"
(`doc/decision/0004-*`); a test checks this distinction explicitly, verifying
both phrases, not just that the strings differ.

`translateErrorCode` reads `csMessages.errors` through next-intl's
`createTranslator` function (works outside React, without
`NextIntlClientProvider`) — inside components, `useTranslations('errors')`
(re-exported from `@lets-park/i18n`, see below) can be used directly instead,
once the tree is wrapped in `IntlProvider`; both paths read the same
`csMessages`, so they can't drift apart.

## Holidays and weekends for the date bar

`isWeekend`, `isCzechPublicHoliday`, `czechPublicHolidayOn`,
`czechPublicHolidays` and `isBusinessDay` are re-exported from
`libs/shared-types` with no behavior change — the 148 tests of the algorithm
(fixed holidays + Easter per Meeus/Jones/Butcher) live there and **are not
repeated here**. `libs/i18n`'s own tests (`shared-types-reexport.spec.ts`) only
verify that the re-export actually works (one fixed holiday, one movable one,
one regular business day), not that the algorithm itself is correct — Task 3
already proved that.

## next-intl: why and exactly how

- **`IntlProvider`** wraps `NextIntlClientProvider` with a hard-coded
  `locale="cs"`, `timeZone={PRAGUE_TIME_ZONE}`, and `messages={csMessages}`.
  `now` is the only overridable prop, purely in case future tests need a
  deterministic clock — production call sites omit it.
- The barrel (`src/index.ts`), besides its own API, also re-exports
  `useTranslations` and `useFormatter` from next-intl — components under
  `IntlProvider` can therefore call them via `@lets-park/i18n` and never need
  a direct `next-intl` import of their own, which would bypass this lib as the
  sole allowed place.
- There's no `i18n/request.ts` / `getRequestConfig` (`next-intl/server`) here
  yet — the app has no locale-based URL routing (a single locale, no
  switching), and wiring it into `apps/web`'s root layout is out of scope for
  Task 17 (which may only touch `libs/i18n/**`). Once `apps/web`'s layout
  exists, it will wrap `children` directly in this `IntlProvider`.
- Jest in `libs/i18n` has to transpile both `next-intl` and `@orpc/contract`
  (both ESM-only), and `errors.spec.ts` runs under
  `@jest-environment node` because of `TransformStream`, which jsdom doesn't
  provide — details, and why this is per-project duplication (rather than a
  change to the root `jest.preset.js`, which Task 17 isn't allowed to touch),
  are in `doc/decision/0025-next-intl-esm-jest-transform.md`.

## Tests

| file | what it verifies |
| --- | --- |
| `dates.spec.ts` | formatting — full date, day+month, month+year, month alone (all 12), year; genitive vs. nominative for August and October |
| `errors.spec.ts` | complete `ERROR_CODES` coverage, `OUT_OF_HORIZON`/`RESERVATIONS_LOCKED` distinguishability, that the translation reads `csMessages` rather than a copy |
| `shared-types-reexport.spec.ts` | weekend, fixed holiday, movable holiday, business day — the re-export works |
| `provider.spec.tsx` | `IntlProvider` actually exposes `useTranslations` to children (a render test) |

## Deliberately missing

- **Language switching / locale-based URL routing** — the app has a single
  locale (Czech); `plan.md` asks for nothing more.
- **`i18n/request.ts` in `apps/web`** — wiring it into the Next.js root layout
  is another task's work (outside `libs/i18n/**`).
- **Pluralization / ICU arguments in `csMessages`** — no message so far needs
  them; once one does, next-intl supports it natively (`t(key, values)`), and
  nothing in `libs/i18n`'s API needs to change.
